# Markdown fields for rich text

Actions that write comments, work item descriptions, and Wiki page content accept a dedicated `*Markdown` field beside the existing editor document field. Supply exactly one representation. Reads retain the editor document and add `markdown` (comments), `descriptionMarkdown` (work items), or `contentMarkdown` (Wiki pages), with a corresponding `*Warnings` array.

Headings, paragraphs, emphasis, links, code, lists, task lists, block quotes, and tables use standard Markdown. Written form uses stable, readable reference forms:

- Mentions: `@{name|member-id}`. The label may be omitted (`@{member-id}`). A bare name resolves only when exactly one visible member or Agent has that name.
- Images: `![[asset:asset-id|Image label]]` (also read as `![[asset-id]]`); the label is optional.
- Callouts: a block quote beginning `> [!note]`, `> [!warning]`, or another simple callout type. Color and icon metadata use `> [!tip|color=#f97316|icon=🚀]`; defaults (`color=null`, `icon=💡`) are omitted. Only editor-guarded colors and the callout picker's icons (`💡`, `ℹ️`, `⚠️`, `✅`, `❗`, `❤️`, `🚀`, `🎉`) are accepted. Invalid metadata is discarded with a warning.
- Inline highlight: `==highlighted text==`; underline, subscript, and superscript use `<u>`, `<sub>`, and `<sup>` respectively.
- A colored highlight uses `<mark data-color="purple">text</mark>`; text color remains `<span style="color:...">`.
- Text color: `<span style="color:...">` accepts a hex color or `red`, `orange`, `yellow`, `green`, `blue`, `purple`, `gray`, `black`, or `white`.
- Work items: `[[ABC-12|work-item:item-id]]`; the key-only form `[[ABC-12]]` resolves only when unique and accessible on work item descriptions, Wiki content, and comments. Pages use `[[Page title|page:page-id]]`, and Wiki pages use `[[Wiki title|wiki:wiki-page-id]]`. Comments resolve title-only Page/Wiki references when unique and accessible; descriptions and Wiki content require the explicit stable-id form for Page/Wiki references. Written links retain the stable id when a title or key changes.

A Work item key is unique within its Workspace across both current Project keys and old-key aliases; the same key may exist in another Workspace. Renaming a key keeps the old key as an alias that resolves to the same Project, and that Project may reclaim its own alias.

Each warning has a stable code and a plain-language message; callers should show the translated message for that code. Formatting may be simplified and non-persisted attributes may be dropped with a warning. Writes are refused only if text, whitespace-normalized link destinations, mention/reference targets, code, or image asset IDs would change.

Unresolved references such as `[[x]]`, `a[[0]]`, and `[[a|b]]` remain plain text with an `unresolved-reference` warning. Literal reference-looking text is escaped when serialized so later reads do not turn it into a link.

Written form imports are limited to 200,000 characters and 64 nested quote/list levels. Before parsing, a linear scan rejects more than 5,000 Markdown delimiters in total, more than 128 within any 1 KB window, a delimiter run longer than 64, or nesting beyond 64 levels. Markdown input is parsed once for the write, and the parsed result is reused for readback checks and storage; conversion time depends on the content, not only the size. Measured for a 200,000-character write on an idle core: 0.14 s for Thai prose, 0.85 s for plain English words, and 3 to 4 s for a document that is dense with bold, links, code, lists and strikethrough; the same dense document takes two to three times longer when the core is shared with other work. The time budget below is sized for that, not for the 0.2 s of plain prose. Excessive inputs return `input-too-complex` or `nesting-too-deep` with a short action message. Only the reserved placeholder characters U+E200 and U+E201 are stripped; other private-use characters are kept as text.

The serializer escapes Markdown punctuation in literal text, including autolink-looking URLs, email addresses, list markers, entities, and reference-looking text. It inserts an invisible word-joiner where needed and removes it when parsing. Reference, mention, and image labels percent-encode reserved delimiters while retaining ordinary spaces. Link destinations with spaces use angle brackets, and code fences are longer than any backtick run in their body. Code-block languages include the editor's supported languages and `mermaid`, which the Page editor renders as a diagram.

Leading and trailing whitespace on marked runs is emitted outside the mark and imports as unmarked text. Where Markdown would consume a boundary space (such as after a list marker or hard break), the serializer uses `&#32;` for that space. Inline code uses the shortest safe backtick fence. Empty continuation lines inside list items contain no indentation whitespace.

An empty paragraph is written as `<!-- empty paragraph -->`. A hard break uses two trailing spaces and a newline in paragraphs; headings and table cells use `<br>`. Separate blocks are separated by a blank line. Lists indent continuation blocks by the marker's content column (for example, three spaces after `3.`). Table cells use invisible HTML comments to retain header/cell roles and mixed block order. Complex table-cell blocks use a validated `wf-cell-blocks` marker; nested callouts, tables, and non-default ordered lists use a validated `wf-block` marker where Markdown nesting would change the text. A headerless first row is preserved with `<!-- wf-cell -->`, for example, `| <!-- wf-cell -->Table block |`; the editor's Table controls can toggle the header row or column.

Attributes the editor does not offer a Written form for are omitted with a warning: asset display width and non-centered alignment, table cell spans/width/alignment, mention typing triggers, custom ordered-list styles, and ordinary link opening target/title/rel/class. Stable internal-link labels use the link text and stable target id.

The CLI accepts a Markdown field as a flag value, or `-` to read it from stdin. MCP tool schemas place the Markdown field first and include an example in its description.

Page and Wiki page Markdown downloads include the Written form and a small invisible title marker so the same file can be imported without duplicating its title heading. Images are clearly referenced as `![[asset:<asset-id>|<label>]]`; the `.md` download does not bundle image files, so an image remains available through its original Weft Asset rather than being copied beside the Markdown file.

## Writing and limits

- **Any plain text can be written.** A block is serialised normally and read back; if its text or links differ, it is written again with every ASCII punctuation character of its text backslash-escaped (with word joiners that stop autolinks and `==`/`[[`/`@{` tokens), and if that still differs, as an exact `<!-- wf-block:... -->` JSON comment. The write is refused (`text-loss`, "Some text or a link could not be saved exactly as written. Nothing was changed.") only when no form reads back with the same text and links.
- **Structure-only differences save with a warning.** Task state, table header role, code language, list start, callout type and image alt each have their own warning code (`task-state-simplified`, `table-header-simplified`, `code-language-simplified`, `list-start-simplified`, `callout-type-simplified`, `image-alt-simplified`); `structure-simplified` covers the rest. A heading level outside 1 to 6 is clamped (`heading-level-simplified`).
- **Parse cost is bounded before remark runs.** One linear pre-scan of the raw text counts leading quote and list markers per line (nesting limit 64, at most 20,000 markers) and stray inline delimiters (a `]` with no `[`, an emphasis closer with no opener, or an opener never closed): at most 1,000 per paragraph and 5,000 per text, otherwise `input-too-complex` / `nesting-too-deep`. Well-formed text has none, so there is no density limit: a 200 KB document of ordinary bold and links is accepted. Markdown the serializer produced, and documents from the editor, skip the stray-delimiter scan (`trustedSource`); nesting and length limits always apply.
- **Live Page saves never throw a save away.** The live state is the source of a Page. If the derived Written form cannot be built, the Yjs state and content are still stored, `contentMarkdown` is derived on a best-effort basis (or left unchanged), and the failure is logged. Page reads (`get_wiki_page`, the Markdown export and the published page) drop unsafe link targets and colours on the way out; the stored Yjs state is not rewritten, so comment anchors keep working.
- **List reads do not parse.** `list_work_items`, `list_workspace_work_items`, `list_sub_work_items` and `list_intake_items` return `descriptionText` and `descriptionMarkdown` and omit `description`. Read one item (`get_work_item`) for the parsed editor document.

## Conversion budget, caps and one Written form

- **Hard wall-clock budget.** Parsing inside remark/micromark can be quadratic on shapes no pre-scan can name (`www.a_` unspaced, repeated fences or escapes). Every conversion above 2 KB runs on a Bun worker (`written-form-pool.ts`), and so does any input of any size that contains `www.`, `=\` + newline, a run of six or more `_`, `*` or `~`, a backtick or `[^` (`needsWorker`); the worst 2 KB input that stays in-process measured under 50 ms. A job's time budget grows with its size: **5 s + 60 ms per KB of input for requests, at most 30 s** (about 17 s at 200 KB, so a dense 200 KB document that needs 4 s on an idle core is still accepted on a shared one), and 20 s + 50 ms per KB for the backfill. The parser runs synchronously and cannot report progress from inside a parse, so the budget is a wall clock, not a progress heartbeat. The clock starts when the thread is ready, so a cold or just-replaced worker does not eat the budget. On timeout the worker is killed and replaced and the write is refused as `input-too-complex` ("This text is too complex to save. Shorten it or split it."). Workers start at boot (`warmWrittenFormPool`) and never hold the process open after the last job.
- **The pool cannot be starved.** Work is split into lanes, each with its own workers, so one kind of input can never occupy the workers that serve another: ordinary requests (`WEFT_WRITTEN_FORM_WORKERS`, default 2), small inputs under 16 KB that merely need a worker (1), suspect inputs (1) and live Page saves (1). A suspect input is one that fails a cheap pre-scan for the quadratic shapes (unspaced runs of `www.`, `=\` + newline, fence + backslash, footnote definitions, `[[` openers): it gets a 3 s deadline, queue wait included, and is refused as `input-too-complex` (or `busy`) when it does not finish. Each lane queues at most `WEFT_WRITTEN_FORM_QUEUE` jobs (default 32); a request past that, or a job still waiting at its deadline (10 s for requests, queue wait included), is refused as `busy`: HTTP 429 with a `Retry-After` header. Workers are handed out round-robin by caller, not oldest first: a caller is the **user** (a token is only a sub-limit of its user, so a user with twenty tokens is still one caller; a request without a user is keyed by address and workspace), and each caller may have 1 job running and 4 waiting per lane. Live Page saves never get a 429: each page may have 1 save waiting and each user 2, suspect saves go to the suspect lane, and a save that cannot be taken degrades as described under Live saves. A worker that crashes or cannot take a job answers 503 `converter-unavailable`; an unknown internal error answers 500 `internal-error` with a generic message (the detail is logged); validation errors stay 400.
- **Configuration.** `WEFT_WRITTEN_FORM_WORKERS` (1 to 8, default 2), `WEFT_WRITTEN_FORM_QUEUE` (1 to 1000, default 32), `WEFT_WRITTEN_FORM_TIMEOUT_BASE_MS` (500 to 60000, default 5000) and `WEFT_WRITTEN_FORM_TIMEOUT_PER_KB_MS` (0 to 1000, default 60). A value that is set but not a whole number in range stops the process at start. The deadlines, per-caller limits and lane sizes other than the first are fixed in code. See `docs/production.md`.
- **Caps.** Text is limited to 200,000 characters (`input-too-long`, "This text is too long to save. Shorten it or split it."); the serialised Written form read back for verification may be 25% longer, but the Written form that is stored must itself fit in 200,000 characters, or the write is refused with the same code. Stored rows are read with their own 1,000,000-character limit and never read blank: a row that cannot be parsed is shown as its raw text in one code-free paragraph (`stored-text-unparsed`). Tables are limited to 20,000 cells per table and 20,000 in all (delimiter rows are not counted; "This table is too large to save. Split it into smaller tables."). A 20,000-cell table measured about 300 MB of process memory growth while converting (`written-form-round7.test.ts` bounds it at 500 MB), which is why the cell cap, not a row cap, is the limit. A document nested deeper than 64 levels is refused as `nesting-too-deep` before it is serialised.
- **One serialiser.** `writtenFormOf` (async, worker-guarded) and `writtenFormOfSync` are the only way to hand out or store Markdown for a document: they write each block normally, then with all ASCII punctuation escaped, then as an exact JSON block comment, and verify by reading it back. Nothing outside `rich-markdown.ts` / `written-form.ts` may call `richTextMarkdown` (a test greps for it).
- **Live saves** never fail on an image the writer cannot use or on a converter failure or timeout, and the version row of a stale save stores no Markdown (empty) rather than the text from before the edit: the Yjs state and content are stored as typed, the image is left out of the derived Markdown (after a limit or timeout the page is flagged `markdown_stale`: search and Outlinks rebuild from `content` until the next successful save clears it), the editor receives a `weft-notice` stateless message, and the failure is logged. API writes refuse a non-uuid image id with `asset-invalid` and an unusable one with `asset-unavailable`.
- **Backfill rows that are too heavy** (too long, too complex, over the cap or timed out) never abort the deploy: the row's text is stored as escaped plain paragraphs **in full** (the 200,000-character write cap applies to new writes, never to the conversion of existing data, so nothing is cut), with no stored document: its legacy document keeps serving until its first edit, and that first editor save is refused with `input-too-long` naming the limit and the current length when its Written form is still over the cap. The row is listed under `degraded` in the report. A row whose Written form would pass the 1,000,000-character read limit keeps its Markdown empty (its legacy document serves) and is listed as `too-large-to-convert`; the comment NOT NULL constraint is applied only when no such comment is left. A row that converts but takes longer than 2 s is reported as `slow-conversion`. Rows are converted outside any transaction (a heavy row cannot hold locks); only the writes, the Outlinks and the NOT NULL changes run in one short transaction, and the report gives the number of rows, the total time, the time inside the write transaction, and the listed rows. The backfill writes with `WHERE <markdown column> IS NULL`, so a concurrent edit is never overwritten.
- **Outlinks** are read from the parsed document (link marks outside code), not from a pattern over the raw text.

## Database backfill

`bun run db:migrate` backfills legacy Work item descriptions, description versions, comments, comment versions, Wiki pages, and Wiki page versions with the conversion outside the transaction and the writes in one. Structural simplifications and dropped attributes are recorded in the report with the table, row id, and warning codes. Only unconvertible rows (for example, unknown editor nodes or invalid Yjs bytes) abort the transaction, with every bad row listed. Backfill writes only Markdown/text columns and Outlinks; it never overwrites the old document JSON or Yjs state, which remain available as rollback sources.

Run `bun run db:migrate --dry-run` after schema migrations have been applied. The dry run is read-only: it does not apply schema migrations or write rows. It prints per-table conversion counts, every simplified row with its warning codes, and every unconvertible row; it exits non-zero only for unconvertible rows.

Reads use the Written form as the current representation for descriptions and comments, deriving editor documents from their Markdown columns. Wiki Pages use valid Yjs state as their live source of truth; if the state is missing or invalid, reads derive the document from `contentMarkdown` before falling back to legacy JSON.

## Reads

`get_work_item` and the comment list convert a stored row once: a large row is parsed on a worker, and the stored Markdown is handed out as it is. It is serialised again only when references the reader cannot open were turned into plain text, and then a timeout returns the stored Markdown, never an escaped copy. `list_work_item_description_versions` returns a page (default 20, at most 100; pass the last id as `after`) of rows with `contentMarkdown` and `contentText`; the parsed document (`content`) comes only with `versionId`, one version at a time.

## Lanes, probation and measured holds

- **Lanes.** Threads: 2 ordinary, 1 small, 1 suspect, 1 live, 1 stored, 1 long. A pre-scan only classifies the fast path; no shape list is trusted. Every ordinary, small, suspect and live job gets a **probation** of 2 s on its own lane. A job that outruns it is aborted and waits on the single **long** lane (20 s deadline, 1 in flight and 2 queued per user), so a hostile input holds an ordinary or live thread for about 2 s, not for its whole budget. A legitimate slow job pays for this: at least 2 s of work is thrown away and it is then serialised on the long lane.
- **Small before heavy.** Within a lane a queued input under 16 KB is taken before a heavy one, then callers round-robin, so a normal save does not wait behind several heavy saves from other users.
- **Stored reads never get a 429.** Reads of stored Markdown run on the stored lane, one batched job per request (`storedReadMany`, per-item progress), with no per-user limit. An item that times out is shown as its raw text (`stored-text-unparsed`).
- **Measured worst-case hold per lane** (197 KB evasive shapes that slip past the pre-scan; `maxHoldMs`, one process, idle machine): ordinary 2.0 s (was 16.3 s), live 2.0 s (was 16.2 s), small and suspect under 2 s (suspect was 3.0 s). The long lane held up to 16.2 s and the stored lane up to 16.2 s on the same shapes; a heavy input that was moved there (or went there directly) waits behind the other moved inputs, one running job per user and two waiting, so heavy documents can be refused as `busy` while attackers loop on the long lane; the stored lane delays only reads of rows without a stored document, which are shown as raw text when they time out. Neither lane serves ordinary or live requests.
- **Link-safe escaping.** After the normal write and before the all-punctuation tier, a tier escapes `://` and `www.` and de-escapes `_` after an alphanumeric, so `http://a_` repeated 20,000 times still stores below the 200,000 cap. A form over the cap is `input-too-long`, checked before text-loss.
- **Version pages.** `list_work_item_description_versions` and `list_comment_versions` take `limit` and `after` and stop a page before its Markdown passes about 1 MB.
- **`rebuild_page_markdown`** (workspace admin) converts at most `limit` stale pages per call (default 25, at most 100) and returns `remaining`; call again until it is 0. It writes only if the page still holds the content it converted (`pagesChangedMeanwhile` counts the pages saved again meanwhile; they stay stale). Pages it cannot convert are listed in `pagesStillStale`.
- **Serialiser call sites.** `writtenFormOfSync` and `richTextMarkdown` are called only by the pool, its worker and the serialiser itself. `plainTextWrittenForm` (linear, no parse-back, 12 ms at 197 KB) is the fallback for legacy rows with no stored Markdown (comments, work items, intake) and for a live save whose conversion failed without a limit. A test lists the files.
- **Known limits.** Whitespace-only differences between a stored form and its re-serialisation are not normalised. A deploy runs the backfill while writers may still be running; stop writers first.

## Round 10: stored documents, per-part Outlinks, fair queuing

- **The Markdown is the original; the document is a cache.** A Work item stores its prepared document in `work_items.description_doc` in the same statement as `description_markdown` (create, update, restore, Intake). A read serves that document and does not parse. Comments already store `body`; Pages carry `content` and `ydoc_state`. A row with no stored document (a degraded backfill row, a version read with `versionId`, a legacy comment) is parsed once on the stored lane, a batch per request, and a timeout shows its raw text. The backfill seeds `description_doc` for the rows it converts and never touches the legacy `description` column. The stored lane is kept for those rows only.
- **Outlinks are kept per part** (`outlinks.source_part`: `body`, `c:<comment id>`, `legacy`; migration 0109). A write replaces only its own part, from the document it just prepared (`referencesInDocument`), so a write never parses another row; the links of a source are the union of its parts. A part that cannot be derived keeps its previous links (`setOutlinkPart(..., null)`), and a part is only replaced after a successful derivation. The backfill and the admin repair rebuild every part from the stored documents (state key `written-form-v2-outlinks`).
- **Fair queuing.** Jobs on a lane are scheduled by a virtual clock and a cost estimate (size, scaled by the density of the characters the quadratic shapes are made of): a newcomer starts at the clock, so a fresh account is scheduled by arrival, not behind every untouched account. A caller whose job outran probation or timed out is **demoted** for 60 s: its next jobs go behind everyone and it may have one job waiting per lane. ****Aging** (after a five-second grace) raises a waiting job's priority with its wait, so a stream of small jobs cannot starve a heavy one. AI chat actions run under `system:ai-chat` and background jobs under `system:worker`; both are limited like a user.
- **Heavy requests and the long lane.** A request of 64 KB or more goes straight to the long lane when it is idle (fewer than two jobs waiting), so no probation is wasted on it. `rebuild_page_markdown` runs on the long lane under the admin's key, takes at most `limit` pages (default 25) after an `after` cursor, returns `next`, and passes pages it cannot convert (listed in `pagesStillStale`).
- **Whitespace.** Spaces and tabs at the edge of a line, and tabs next to a hard break, are written as character references and read back exactly; a hard break stays a hard break. What cannot be kept (a byte-order mark U+FEFF, which the parser strips) is reported as `whitespace-simplified` with a message naming it, not as a generic structure change.
- **Limits.** Over the 200,000-character cap, the shortest form that reads back (no backslash before a parenthesis or an underscore inside a word) is tried before a write is refused, so `my_var_name ` repeated for 190,000 characters is accepted. A text with more than 2,000 `[[` is refused at once (`input-too-complex`, "more than 2,000 [[ brackets"), before it queues for a worker.
- **Export.** The Markdown export writes images as `![[asset:<id>]]` tokens and does not include the files: they show only inside Weft. The export menu says so. Writing images as relative files in a zip is not done (known limit).
- **History.** Description versions and comment versions page by cursor (`limit`, `after`) in the UI with "Show older versions"; a first page that fails to load shows an error with a retry.
