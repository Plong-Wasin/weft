# Running Claude and Codex in an OS sandbox

## Summary

For ticket 22, use Anthropic Sandbox Runtime (`srt`) as the first common OS-level wrapper prototype, with a fail-closed launcher owned by the Daemon. It is the only option tested here that gives the same explicit file and host allowlists to arbitrary child processes; Codex's built-in sandbox completed a real task too, but its standard workspace-write profile includes `/tmp` and does not express this prototype's provider + Weft + Git domain set. Claude Code has a built-in sandbox, but its configured runtime files and hooks need a clean per-Run config directory to avoid writes outside the Run.

This is a recommendation for a follow-up prototype, not a production security approval. The SRT run proved the Linux file/network boundaries and completed a real Codex Run. It could not reach a Daemon/API service on host `localhost`, macOS was not available, and the current Daemon does not start children through a sandbox. Ticket 22 must resolve the Run-token exposure and local Weft callback before enforce mode is safe.

## Findings

### What was run

Host: Linux Mint 22.1 / Ubuntu 24.04 base, x86-64, kernel `7.0.0-31-generic`, Node `24.12.0`. No repo Daemon or Compose services were started. `srt` `0.0.83` was installed under `/tmp/weft-sandbox-research` with `npm install --prefix /tmp/weft-sandbox-research @anthropic-ai/sandbox-runtime`; it was not installed globally. SRT itself requires Node.js `>=22.12.0`. Host dependencies were already present: `bubblewrap 0.9.0`, `socat`, and `ripgrep 15.2.0`. No administrator action or system setting change was made.

The repeatable OS-boundary checks are in [`tools/sandbox-prototype/run.sh`](../../tools/sandbox-prototype/run.sh). Its disposable tree and package installation are removed on exit. A real Codex CLI task was run from the session scratchpad's disposable `sandbox-runtime-check/run` directory. SRT `0.0.83` was installed under that scratchpad, `CODEX_HOME` held a temporary copy of the Codex login/config files, and the child started with a clean `env -i` environment containing only `HOME`, `CODEX_HOME`, `TMPDIR`, and a curated `PATH` plus SRT's proxy variables. It created `codex-task.txt` with `sandbox task complete` and exited successfully. The copied login files, CLI binary, helper, and workspace were removed after the experiment. This proves Codex can run under SRT when its provider domains and config access are supplied, not that SRT itself authenticates the user.

### SRT: demonstrated behavior

The profile denied reads of `~/.config/weft`, `~/.ssh`, `~/.aws`, `~/.azure`, `~/.config/gcloud`, and two existing synthetic credential files. A write in the Run directory succeeded; a write to its parent failed with `Read-only file system`. `https://api.openai.com/` returned HTTP 421 (network reached); `git ls-remote https://github.com/octocat/Hello-World.git HEAD` succeeded. `https://example.org/` failed with `CONNECT tunnel failed, response 403`. These are observable results from the prototype script / manual run.

The model provider list must reflect the CLI auth mode, not only the inference endpoint. The first Codex attempt failed its login/model routing calls because `chatgpt.com` was missing; after adding `chatgpt.com`, `*.chatgpt.com`, and `auth.openai.com` alongside `api.openai.com`, the real Run completed. Claude's first attempt also showed startup writes: it failed creating `/tmp/claude`; setting `CLAUDE_CODE_TMPDIR` inside the Run got past that point, but this workstation's user-installed Claude hook then failed trying to write its Orca spool under `~/.config/orca`. A production daemon should provide a clean per-Run CLI config/home with only the login material the CLI needs, and must not load a person's unrelated hooks, plugins, skills, or session history. Whether each login method can be moved that way needs a separate test for both CLIs.

Git HTTPS clone from GitHub succeeded. Git SSH clone to `git@github.com:octocat/Hello-World.git` failed: SSH's direct path and the user's agent socket are not a usable default in the sandbox; SRT injects a `socat` proxy command, but the test had no allowed SSH credential. SSH support is therefore unverified, and should not be assumed to work by forwarding `SSH_AUTH_SOCK`. `npm install left-pad` failed because the npm registry was deliberately outside the allowlist. Package installs need `registry.npmjs.org` and any redirect/content hosts explicitly allowed; this widens the egress surface. A `weft` callback to `http://localhost:3000` failed because SRT's Linux sandbox has its own loopback. The coordinator provided the API's host-published address; with `WEFT_TEST_URL=http://192.168.1.127:3000/api/me`, the prototype received HTTP 401 using a deliberately invalid test token. This proves callback network routing to the live Weft endpoint without creating or changing data; valid Run-token authentication remains unverified. The private host:port must be allowlisted and sent through the SRT proxy (`NO_PROXY` bypasses private addresses here); using `localhost` cannot reach the host service. SRT itself uses a Unix-socket proxy bridge on Linux, but no Weft-specific Unix-socket forwarding route was tested.

SRT's documented model is Linux bubblewrap + isolated network namespace and a proxy, and macOS Seatbelt (`sandbox-exec`). Linux needs `bwrap`, `socat`, and `rg`; Ubuntu 24.04 may need an administrator to change the AppArmor user-namespace restriction or add an AppArmor rule when the host policy prevents unprivileged namespaces. That setting was not changed here. SRT's package documentation says macOS needs `rg`, with no extra system package; Seatbelt behavior was not run on a Mac and remains unverified. SRT's own docs describe local loopback as isolated on Linux and require proxy-mediated traffic; this explains why a localhost Weft URL is not reachable. See [SRT platform/dependency notes](https://github.com/anthropics/sandbox-runtime/blob/main/README.md#platform-support) and [configuration behavior](https://github.com/anthropics/sandbox-runtime/blob/main/README.md#common-configuration-recipes).

### CLI built-in sandbox comparison

Codex CLI `0.167.1` completed a real task in `codex exec --ephemeral --sandbox workspace-write` from a disposable `/tmp` workspace. Its output identified `workspace-write [workdir, /tmp, $TMPDIR]`; so the default profile is broader than “write only in the Run folder.” Codex supports explicit workspace roots in its config, but a custom root profile and per-domain network policy were not validated in this prototype. Its normal network policy is a broad enabled/disabled choice at the CLI sandbox seam, not the same SRT host allowlist. Linux requires bubblewrap (with a bundled helper fallback under supported user-namespace policy); macOS uses the operating system's Seatbelt framework and needs no extra package. The native Codex sandbox and SRT are not composable by default: SRT's Linux restrictions prohibit nested user/mount namespaces, which Codex's own sandbox may need. Choose one boundary rather than wrapping Codex's default sandbox inside SRT. See [Codex sandbox guidance](https://developers.openai.com/pt-BR/docs/sandboxing) and the [Codex config implementation](https://github.com/openai/codex/blob/main/codex-rs/config/src/config_toml.rs).

Claude Code exposes a built-in sandbox on macOS and Linux, with filesystem and domain controls; it is built on SRT. Linux requires `bubblewrap` and `socat`, with an optional seccomp filter; macOS uses built-in Seatbelt. However, Anthropic documents that the sandbox applies only to shell commands: Claude's Read/Edit/Write/Web tools, hooks, MCP servers, plugin monitors, and LSP servers run outside the sandbox. That makes the built-in mode insufficient as the OS boundary around the complete CLI process. The shell boundary can be configured to refuse startup when unavailable (`sandbox.failIfUnavailable: true`), and Claude's built-in model is promising for a later dedicated profile if the Daemon can also constrain those out-of-sandbox processes. Our local command-level evidence above is that the user-installed hook tried to write outside the Run, and `CLAUDE_CODE_TMPDIR` fixed only the CLI temp path. Anthropic documents the [sandbox scope and dependencies](https://docs.anthropic.com/en/docs/claude-code/sandboxing), [login setup](https://docs.anthropic.com/en/docs/claude-code/getting-started), and [provider/auth hosts](https://docs.anthropic.com/en/docs/claude-code/corporate-proxy); no direct built-in-vs-SRT benchmark on macOS was possible.

## Recommendation for ticket 22

Prototype SRT behind a Daemon adapter that constructs a complete per-Run settings file and launches `srt --settings <file> -- <cli> ...`. Before Run start, resolve the configured SRT executable, verify its version and `bwrap`/`socat`/`rg` dependencies, then launch a harmless startup probe under the exact profile. A missing executable, dependency, unsupported OS, or rejected sandbox startup must fail the Run with an actionable install/host-policy message; it must never retry the child unsandboxed. Treat namespace/AppArmor startup refusal as unavailable, not as permission to retry without SRT. Use the selected agent CLI's native sandbox only as a separate opt-in profile until it can demonstrate the same effective paths, domains, callback behavior, and missing-tool refusal.

Build the per-Run filesystem policy from canonical Run and credential paths: write only the real Run directory; deny Weft config, SSH, and cloud credential roots; do not mount the repository checkout or all of `$HOME` as writable. A CLI's own authentication/session directory must be deliberately provisioned per Run. Keep the SRT settings file outside agent-writable content and mode `0600`.

Pass the short-lived **Run token** and context through a clean environment, not the Daemon credential or Personal API token. Retain the existing `WEFT_API_URL`, `WEFT_TOKEN`, `WEFT_RUN_ID`, `WEFT_WORKSPACE_ID`, `WEFT_PROJECT_ID`, `WEFT_WORK_ITEM_ID`, `WEFT_COMMENT_ID`, and `WEFT_TRIGGER_ID` contract from `childEnvironment`; clear all other host variables, and give the model CLI only the auth material it requires. The current design exposes `WEFT_TOKEN` to the agent process. SRT host allowlisting does not stop that process from placing a readable token into a request to an allowed model host. Ticket 22 must test SRT credential masking/injection or a brokered Weft callback before claiming that the token cannot be exfiltrated. Credential masking needs SRT's TLS-terminating proxy and trust setup, which was not enabled here.

Network policy must include each selected model/auth host, the configured Weft API hostname:port, and Git HTTPS hosts (`github.com`, `api.github.com`, `*.github.com`, and `lfs.github.com` when needed). Never assume one provider list works for both CLIs or auth methods. For a private LAN Weft callback, remove SRT's generated `no_proxy`/`NO_PROXY` entries from the CLI's environment (`env -u no_proxy -u NO_PROXY <cli>` in the prototype) so that the request uses SRT's proxy and host:port allowlist instead of the sandbox's blocked direct private-network route. `localhost` still resolves to the sandbox's own loopback; production should provide a routable API hostname/address or a specifically supported proxy/socket bridge. Do not treat SSH cloning, npm installs, browser login flows, or user hooks as supported until separately tested.

## Open risks and unverified claims

- macOS SRT and built-in CLI sandboxes were not run. Linux results do not prove Seatbelt policy behavior.
- No live Weft API was available. The local callback was denied by namespace isolation; a public/deployed Weft hostname and server-side callback test remain to be run.
- Real Claude completion and its OAuth/session-file behavior under a clean per-Run config were not proven. Its workstation hook was an environmental confounder and must be absent in a daemon child.
- SRT credential masking, TLS interception trust, and whether the CLI's Weft client is compatible with it were not tested.
- SSH Git, npm registry installs, Git LFS, package redirects, cloud CLIs, and GUI/browser login were not proven. User-visible behavior may need additional allowlisted hosts or explicit refusal.
- SRT's allowlist controls ordinary proxy-aware egress; this experiment did not audit every OS service, resolver, or intentional sandbox escape.
- Admin changes may be required for Linux user namespaces/AppArmor. They were not made.
