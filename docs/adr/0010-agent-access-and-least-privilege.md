# Agent access is per person, and Agents start with least privilege

Supersedes the "deletions still need a Confirmation" limit of ADR 0009 for Agents and replaces the personal-token Daemon sign-in it implied. ADR 0009 stays in force for everything else.

Project write permission cannot decide who may start a Run, because a project's PM and developers hold the same role while only developers should wake an Agent that changes code on a colleague's computer. So every Agent has **Agent access**, a list of people kept per Agent: a Code-capable Agent starts with its Runtime owner alone and the owner extends it person by person; any other Agent starts open to the members of its projects. Assigning or mentioning an Agent without access is refused by the server (UI, API, CLI, and MCP alike); the pickers show such an Agent greyed out with the reason. We chose per-person lists over groups or roles to avoid a new permission system for a small company; groups can come later.

An Agent starts with only work-item and comment actions in the projects it belongs to. Project, member, feature, and export actions are off for server and Runtime Runs alike, and an owner switches more on per Agent. An Agent can never delete: it gets a refusal, not a Confirmation, on both paths, so the Confirmation mechanism is not extended to Runtime Runs. The Daemon signs in with its own credential that reaches Daemon endpoints only and expires and rotates, so a child process that reads it cannot call `/actions` as the person; the agent CLI is started with a filtered environment. Login tokens get a default expiry. Runtime Runs use the Agent's timeout, and Run creation is rate-limited per person and per Agent. Changes to Agents, Runtimes, Triggers, Skills, Agent access, and Autopilot are written to the activity log, and unsharing a Runtime or disabling an Agent cancels its running Runs and fails the queued ones with a note on the work item.

We did not add a sandbox per Run (container or bubblewrap): the agent CLI still runs as the Daemon's OS user and can read what that user can read, so these steps limit what a leaked credential can do, not what an Agent can touch on its owner's computer. A sandbox is deferred as a proposal because it changes how Agents reach repositories and git credentials.
