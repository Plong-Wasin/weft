# Agents run server-side as the originator and every write needs Confirmation

An Agent is a bot user, a workspace member that is not a person. Assigning it a work item or mentioning it in a comment queues a Run. `apps/worker` executes the Run as a server-side tool loop on the configured model, calling the same Actions as the UI and the AI chat. No code execution and no local agent CLI. The worker calls the Actions in-process with the Originator's context, so an internal Run needs no token; only external agents over HTTP will get a hashed, run-bound token. A Run keeps no state in worker memory: its steps live in `run_messages`, so a Confirmation or a crash resumes it from the stored transcript.

A Run has exactly the permissions of its Originator, the person who assigned or mentioned the Agent. If that person cannot access the project, no Run is created. Every Write action a Run proposes becomes a Confirmation for the Originator. The Run then waits (`waiting_confirmation`) and resumes when the Originator decides. A Confirmation that expires after 24 hours fails the Run without retry. The only write that skips Confirmation is the Agent's own reply comment. Work item text, comments, and wiki content enter the prompt as untrusted data. Changes made by an Agent never trigger event triggers, and an Agent's comment never starts a Run, so Agents cannot wake each other.

We rejected an auto-approve switch (ADR 0002 already defers it) because an asynchronous Run reads data that other people wrote, and nobody is watching it. Plane's own Agents have no approval gate, only its chat Build mode; we accept slower Runs for that safety. We rejected a polymorphic `assignee_type` in favour of bot users so that assignees, mentions, and pickers keep working unchanged. Every Run has a step limit, a token limit, and a timeout, and each Agent has a monthly token budget.
