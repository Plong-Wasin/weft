# Agent access is per person, and Agents start with least privilege

Supersedes the "deletions still need a Confirmation" limit of ADR 0009 for Agents and replaces the personal-token Daemon sign-in it implied. ADR 0009 stays in force for everything else.

Project write permission cannot decide who may start a Run, because a project's PM and developers hold the same role while only developers should wake an Agent that changes code on a colleague's computer. So every Agent has **Agent access**, a list of people kept per Agent: a Code-capable Agent starts with its Runtime owner alone and the owner extends it person by person; any other Agent starts open to the members of its projects. Assigning or mentioning an Agent without access is refused by the server (UI, API, CLI, and MCP alike); the pickers show such an Agent greyed out with the reason. We chose per-person lists over groups or roles to avoid a new permission system for a small company; groups can come later.

An Agent starts with only work-item and comment actions in the projects it belongs to. Project, member, feature, and export actions are off for server and Runtime Runs alike, and an owner switches more on per Agent. An Agent can never delete: it gets a refusal, not a Confirmation, on both paths, so the Confirmation mechanism is not extended to Runtime Runs. The Daemon registers with the owner's Personal API token, a normal token saved by `weft login` with a 30-day expiry, and receives its own Daemon credential. That credential reaches `/api/daemon/*` endpoints only, expires after 30 days, and rotates when less than 7 days remain. The agent CLI is started with an allowlisted environment that never contains the Daemon credential or a `WEFT_DAEMON_*` variable, but it runs as the same OS user with the same `HOME`, so it can read the credential file and the saved Personal token. The Personal token can call `/actions` as the owner, so a Run can reach past the Agent's permissions through it; this is a known gap until the sandbox below exists, not something the environment filter prevents. Runtime Runs use the Agent's timeout, and Run creation is rate-limited per person and per Agent. Changes to Agents, Runtimes, Triggers, Skills, Agent access, and Autopilot are written to the activity log, and unsharing a Runtime or disabling an Agent cancels its running Runs and fails the queued ones with a note on the work item.

We did not add a sandbox per Run (container or bubblewrap): the agent CLI still runs as the Daemon's OS user and can read what that user can read, including the credential files. The steps above limit what a leaked Daemon credential can do in Weft; they do not limit what an Agent can touch on its owner's computer, and they do not stop a Run from reading the Personal token. A sandbox is deferred as a proposal because it changes how Agents reach repositories and git credentials; it is the step that would close the Personal-token gap.

Documented read-only exception: `list_work_item_pull_requests` stays in the no-grant base list because it only shows pull request links that are already part of a work item the Agent can see; every other integration action is people-only.
